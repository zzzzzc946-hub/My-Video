# 跨视频剪辑记忆闭环设计

**目标：** 让每个新开的 MAX 剪辑窗口在不全文加载历史日志的前提下，读取此前视频已确认的剪辑经验，并将本条经验可追溯地回流到同一 GitHub 真源。

## 已确认事实与问题

- `CHEN-BRAIN/main` 已是正式规则与知识文本的唯一真源；新任务会读取 `00`，并按路由检索 `03` 和 `06`。
- `03` 管稳定规则，`06` 管校准证据与例外；单条视频的完整过程应保留在该视频日志。
- 当前没有“视频复盘索引”这一中间层。仅存在于已关闭聊天窗口、但未写入文件的总结不可可靠检索，不能被视作已经继承的长期记忆。

## 方案选择

采用“索引 + 结构化复盘包 + 定向检索”。不采用每次全文读所有历史日志（上下文膨胀且容易把单条偏好误当规则），也不新增独立数据库（会增加维护面和双机同步风险）。

## 数据边界

在 `CHEN BRAIN/03｜CHEN操盘手系统/03｜MAX剪辑系统/` 内新增：

- `07｜视频复盘归档/`：每条已完成视频一个不可覆盖的 Markdown 复盘包，记录视频标识、规则 SHA、主题标签、结果、可复用候选、反例、关联规则/校准与原始任务日志位置。
- `07｜视频复盘索引.md`：只保存每条复盘的简洁索引项和主题标签，不复制规则正文或完整时间码。

原始视频、EDL、成片、逐字稿、缓存仍留在单条视频项目中；归档包只引用其路径与版本，不复制或移动它们。

## 新视频启动流程

1. 快进拉取 `CHEN-BRAIN/main`，记录规则 SHA。
2. 读取 `00`，并按既有路由读取 `01/02/03` 和相关 `06`。
3. 根据本条视频的主题、内容类型、结构问题、用户反馈类型，从 `07｜视频复盘索引.md` 选取最相关的少量归档包；只读取这些包。
4. 将“本次读取的复盘 ID、继承判断和不适用原因”写入本条任务卡/日志。归档包是证据与案例，不覆盖 `01–03` 的正式边界。

## 视频结束与裁决流程

1. 每条视频在交付前或交付后形成一个结构化复盘包；没有复盘包不得把该窗口称为已完成记忆回流。
2. 决策中枢先检索 `03`、`06`、索引和相近归档包，随后把每项发现裁决为：不写入、合并证据、新建 F1、修订/升级或本条经验。
3. 已裁决的规则写入既有 `03/06`；单条经验留在复盘包。更新索引后随同 Git 提交推送。
4. 第二台电脑只可提交结构化候选/复盘包；当前电脑仍是唯一正式规则写入者。NAS 只镜像 Git 已确认的版本。

## 迁移与失败处理

- 已落盘的历史总结按同一模板补录、检索和去重；每一份保留其来源与“历史补录”状态。
- 未落盘的聊天内容不猜测、不补造。用户提供原文或保存路径后才补录。
- Git 拉取或推送冲突时停止写入，重新拉取并对相同主题的归档包做去重裁决；禁止强推。

## 验收

- 新窗口启动清单明确要求读取正式规则、相关校准和定向历史复盘，并记录所读复盘 ID。
- 每个交付视频都有一份可定位的复盘包和一个索引项。
- 相同主题的经验不会在索引、`06` 和 `03` 中重复堆叠。
- 新机制不读写原片、EDL、成片、渲染缓存或 NAS。
