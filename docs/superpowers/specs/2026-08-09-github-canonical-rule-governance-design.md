# GitHub 规则主库与双机剪辑治理设计

## 目标

让两台电脑可并行剪辑并持续产出规则经验，同时保证 MAX `00–07` 正式规则只有一条可追溯的演化线。GitHub 是规则与文本的唯一正式真源；当前这台电脑是长期唯一决策中枢；NAS 仅保存 GitHub 已确认版本的单向镜像。

## 仓库边界

建立独立的 `CHEN-BRAIN` GitHub 仓库，只追踪文本知识与治理文件：MAX `00–07`、规则候选、模板、必要 Markdown/JSON 与同步元数据。它不包含原片、成片、缓存、代理、工作台草稿、`.env`、密钥或机器专属 Obsidian 状态。

现有 `My-Video` 继续保存 VideoUse 工作台、Skill、代码和视频项目文档；不承担 MAX 正式规则正文。

## 本地与远端关系

两台电脑各自维护本地 `CHEN BRAIN` Git 工作副本，所有读取和写入发生在本地副本。GitHub 的默认分支是唯一正式版本；每次任务启动前使用快进拉取获取规则快照。NAS 中的同名目录只从已推送的 Git 提交单向镜像，并记录来源提交 SHA；NAS 文件永不反向覆盖 GitHub 或本地副本。

## 写入模型

正式规则路径为 `rules/00–07/`。只有当前这台电脑的“决策中枢”可修改该路径。

每条视频在结束时只能新建独立候选文件 `inbox/open/<UTC时间>__<机器ID>__<视频ID>.md`。候选必须包含：候选 ID、机器 ID、视频 ID、任务开始规则 SHA、目标规则编号、裁决建议、可执行判断、证据/时间码、适用范围、例外与冲突提示。候选可由任意电脑提交和推送，但不得修改正式规则。

决策中枢拉取候选后，检索规则、证据库与已有候选，并在单个提交中完成以下之一：拒绝、合并证据、新建候选规则、修订/升级正式规则、标记 REVIEW。已处理候选移至 `inbox/processed/` 并保留其裁决；正式规则正文只保留精简、稳定结论。

## 并发与故障处理

- 每条视频绑定任务开始时的规则 SHA；任务中不因远端更新改变其判断基础。
- 候选使用独立文件，因此不同视频并发提交可自动合并。
- 任何修改正式规则前，决策中枢必须 `git pull --ff-only`。推送被拒绝时停止写入，重新拉取、检索和裁决；禁止强推。
- 离线电脑可本地保存候选，恢复网络后先拉取再推送；不得用旧本地版本覆盖远端。
- NAS 与 GitHub 的 SHA 不一致或 NAS 出现手工改动时，生成 REVIEW 记录；不自动反向同步。
- 同一视频、EDL、VideoUse 工作台草稿仍只允许一台电脑编辑；Git 只同步规则和可审计文本。

## 日常协议

1. 开始视频：拉取正式规则、记录规则 SHA、创建本地任务记录。
2. 结束视频：创建独立规则候选、提交并推送；不改正式规则。
3. 决策中枢：拉取全部候选、执行去重与冲突裁决、提交正式规则与候选状态。
4. NAS：仅在用户要求、规则确认后或备份时，由决策中枢将 GitHub 已确认版本单向镜像到 NAS 并记录 SHA。

## 验收标准

- 另一台电脑不能通过 NAS 或本地路径直接改写正式规则。
- 两台电脑可同时提交不同视频的候选，且不丢失任一候选。
- 每条正式规则改动可追溯至 Git 提交与候选证据。
- 本机落后、离线、推送竞争和 NAS 漂移都不会造成静默覆盖。
- 当前这台电脑是唯一正式规则合并者。
