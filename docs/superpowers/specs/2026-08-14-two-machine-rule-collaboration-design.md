# 双机剪辑规则协同与仓库统一最终设计

- **状态：** 已完成第一性原理与对抗性审查，等待实施
- **决策中枢：** 当前主电脑
- **长期剪辑节点：** 另一台电脑
- **默认剪辑工具：** VideoUse

## 1. 目标与保证边界

两台电脑都可以长期剪辑、读取历史经验并沉淀新证据，但系统必须保证：

1. `CHEN-BRAIN/main` 是 MAX 正式知识与规则的唯一真源。
2. `My-Video/main` 是工作台代码与 `max-jianji-skill` 发布版本的唯一真源。
3. 当前主电脑是唯一决策中枢；只有它能裁决候选、修改正式规则、发布 Skill 与工作台。
4. 另一台电脑只新增不可覆盖的候选，不直接改写正式规则、Skill 或工作台。
5. 每条视频使用启动时冻结的规则与候选快照，不因远端中途变化静默改变判断基础。
6. 未裁决经验不能静默进入正式层，也不能因被重复试用而自动晋升。
7. 并发、断网、过期版本、路径越权或发布不完整时必须停止，不自动覆盖、不强推。
8. NAS 只接收 Git 已确认版本的阶段性镜像，不参与规则写入、合并或冲突裁决。

本设计防止标准工作流中的误操作、静默覆盖和并发丢失。仓库所有者主动关闭保护规则或绕过检查，不属于系统可保证范围；任何临时绕过都必须由用户明确授权并留下审计记录。

## 2. 不可破坏的项目边界

- 原片、原始 EDL、成片、转写全文、代理、缓存和渲染产物不进入两个规则仓库。
- 不移动、不覆盖 NAS 原片、历史产物或其他电脑的工作草稿。
- 每条视频使用独立 VideoUse 项目；同一个 `working-draft.json`、`events.jsonl` 或 EDL 不允许双机同时编辑。
- 所有发送给 MAX 审片的粗剪、复核、版本对比和最终候选固定为 **1080P、30 fps**；原片、原始 EDL 与指定母版不因此改变。
- Skill 保存启动顺序、工具路由、成本、质量和回流协议；具体剪辑判断只保存在 CHEN-BRAIN 正式层，禁止双仓复制同一判断正文。

## 3. 真源、身份与权限模型

### 3.1 仓库职责

| 仓库 | 默认分支 | 保存内容 | 不保存内容 |
|---|---|---|---|
| `zzzzzc946-hub/CHEN-BRAIN` | `main` | 正式 00–07、候选 08、裁决记录、规则发布清单 | 视频、EDL、渲染产物、密钥、机器绝对路径 |
| `zzzzzc946-hub/My-Video` | `main` | VideoUse 工作台、Skill、测试、项目治理文档 | MAX 正式判断正文、原片和历史成片 |

### 3.2 GitHub 身份

为获得服务端硬隔离并通过生产验收，必须采用两个 GitHub 身份：

- 决策中枢使用仓库所有者或正式维护者账号。
- 另一台电脑使用独立协作者账号，只负责候选分支与候选 PR。

若两台电脑使用同一所有者账号，服务端无法证明物理机器身份。此时专用命令和路径检查仍能防止标准流程中的误操作，但不能阻止账号持有人主动绕过规则，因此只能作为过渡状态，不能宣告双机机制完成验收。

### 3.3 本机角色

两台电脑各自保存被 Git 忽略的 `config/machine-role.json`：

```json
{ "role": "decision-hub", "machineId": "max-primary" }
```

```json
{ "role": "editor", "machineId": "max-secondary" }
```

本机角色只用于选择命令、提前报错和生成机器 ID，不是最终权限边界。最终边界由受保护分支、PR 差异检查、CODEOWNERS 和必需状态检查共同提供。

## 4. 规则数据模型

### 4.1 正式层

正式层包括：

- `00｜MAX剪辑系统入口与读取顺序.md`
- `01｜MAX剪辑画像.md`
- `02｜MAX账号与受众.md`
- `03｜MAX粗剪判断标准.md`
- `04｜MAX自有视频案例库.md`
- `05｜外部对标视频案例库.md`
- `06｜MAX剪辑反馈与校准库.md`
- `07｜视频复盘索引.md` 与已裁决复盘归档
- CHEN-BRAIN `08｜规则候选收件箱/governance/` 中的审阅批次与规则发布清单
- My-Video 中的 `max-jianji-skill/SKILL.md`

正式层只允许通过决策中枢的正式发布 PR 修改。

### 4.2 候选层

候选层位于：

```text
03｜CHEN操盘手系统/03｜MAX剪辑系统/
└── 08｜规则候选收件箱/
    ├── open/
    ├── processed/
    └── governance/
        ├── review-batches/
        ├── releases/
        └── current-release.yaml
```

另一台电脑只能在 `open/` 新增一个全新 Markdown 文件，不得修改、覆盖、重命名或删除任何已有文件，也不得更新共享索引。

文件名固定为：

```text
CR-YYYYMMDD-HHMMSS-机器ID-视频ID-随机短码.md
```

候选必填字段：

- `candidate_id`
- `machine_id`
- `video_id`
- `created_at`
- `formal_start_sha`
- `candidate_snapshot_ids`
- `submission_base_sha`
- `topic_tags`
- `content_type`
- `editing_problem`
- `user_feedback_summary`
- `evidence`
- `proposed_rule`：条件 → 动作
- `scope`
- `exceptions`
- `counterexamples`
- `related_formal_rules`
- `related_calibrations`
- `related_candidates`
- `duplicate_of`
- `conflicts_with`
- `trial_result`
- `status`

新候选状态只能是：

- `OPEN_UNTRIED`：尚未在真实视频中验证。
- `OPEN_VERIFIED_ONCE`：仅在本条视频中得到一次证据。
- `REVIEW`：与正式规则、其他候选或证据发生冲突。

候选不得包含密钥、`.env` 内容、机器绝对路径、完整转写或无必要的私人信息。日志只写逻辑视频 ID、相对项目标识和必要时间码。

### 4.3 已处理状态

决策中枢处理候选后，将其移动到 `processed/`，并填写且冻结：

- `disposition`：`REJECTED / EVIDENCE_MERGED / PROMOTED / REVISED / VIDEO_ONLY / NEEDS_MORE_EVIDENCE`
- `decision_reason`
- `release_id`
- `target_rule_ids`
- `supersedes`
- `processed_at`

移动到 processed 时，原始候选正文保持不变，只追加裁决区块；合并后 processed 文件不可再次改写。后续新证据必须创建新候选并引用原 Candidate ID。处理提交可由 Git 历史和 `release_id` 唯一追溯，不在文件内写无法自引用的当前提交 SHA。

## 5. 每条视频的冻结读取协议

两台电脑在每条视频启动时必须执行同一预检：

1. 验证两个仓库 remote、默认分支、本机角色和工作区状态。
2. 对 CHEN-BRAIN 执行 `fetch` 与 `pull --ff-only`，记录 `formal_start_sha`。
3. 读取当前规则发布清单，确认其要求的 My-Video 最低提交是本机 My-Video HEAD 的祖先；不兼容则停止。
4. 对 My-Video 执行只读快进同步，记录 `my_video_start_sha`。
5. 读取正式 `00`，按路由定向读取相关 `01/02/03/06/07`。
6. 只扫描 open 候选的结构化头部，按主题、内容类型、剪辑难点和关联规则排序。
7. 最多选择 **3 条**相关候选，记录 Candidate ID、选择理由、冲突和是否允许试用。
8. 将正式 SHA、My-Video SHA 和候选 ID 集合冻结到任务日志，直到本条视频交付。

每条视频启动时同时创建带 Token Budget 的 Goal。交付时任务日志必须记录实际 Token Usage、制作总耗时、人工等待时间、转写次数、渲染次数、返工次数与最终成片时长，并计算“每分钟成片 Token 成本”。完整任务日志不进入规则正文；只有经过检索与裁决的精简经验进入候选或正式层。

判断优先级固定为：

```text
当前用户明确指令
→ 正式硬边界与稳定规则
→ 已确认校准
→ 当前素材证据
→ OPEN 候选
```

候选默认只能触发额外检查、保守处理或有记录实验，不能直接覆盖正式判断。候选与正式规则冲突时正式规则优先；候选之间冲突时不得混合执行。需要偏离正式规则时，必须由用户在当前视频中明确确认，该确认仍只形成候选，不自动改写正式层。

视频执行期间即使远端规则或候选发生变化，也不自动刷新当前任务。只有用户明确要求重新基线化时，才重新读取并在日志记录旧、新快照与影响。

## 6. 另一台电脑的候选提交事务

候选提交只能通过专用命令完成，不允许使用通用 `git add -A`。专用命令采用临时工作树或临时 clone，避免把剪辑工作目录里的误改带入提交。

事务顺序：

1. 检查角色为 `editor`，remote 与仓库 ID 正确。
2. 对候选草稿执行正式规则、06 和 open 候选检索，填写重复、关联和冲突字段。
3. 从最新 `origin/main` 创建 `candidate/<machine-id>/<candidate-id>` 分支。
4. 校验文件名、唯一 Candidate ID、必填字段、状态、路径和内容限制。
5. 只向临时工作树复制并暂存该一个候选文件。
6. 验证 Git diff 恰好是 `08/open/<Candidate ID>.md` 的一次新增；修改、删除、重命名或多文件变更全部拒绝。
7. 提交并普通推送候选分支，创建候选 PR。
8. 启用候选 PR 自动合并；只有服务端 `governance-gate` 通过后才能进入 `main`。
9. PR 失败或 base 过期时，重新从最新 `origin/main` 创建干净候选分支；不在正式文件上自动合并，不强推共享分支。
10. 确认 PR 已合并后才清理临时分支；原候选草稿在合并确认前保留。

候选提交命令不提供正式规则、processed、Skill、工作台或工作流文件的写入参数。

## 7. GitHub 服务端闸门

### 7.1 CHEN-BRAIN/main

`main` 必须启用：

- 禁止直接 push，所有变更必须通过 PR。
- 必需状态检查 `governance-gate`。
- 禁止 force push 和分支删除。
- 对管理员同样执行保护规则；任何 bypass 默认为空。
- 正式 00–07、processed、发布清单、工作流和治理脚本由决策中枢账号 CODEOWNERS。

`governance-gate` 将 PR 分为两类：

**候选 PR**

- 只能新增一个 `08/open/*.md`。
- 禁止修改、删除和重命名。
- 校验字段、Candidate ID、文件名、绝对路径、秘密和禁止文件类型。
- 不修改正式规则，因此通过后可自动合并。

**正式治理 PR**

- 只允许由决策中枢流程发起并人工合并。
- 每个被处理候选必须出现在固定审阅批次中。
- 正式规则变化必须有裁决、证据、目标规则 ID 和 `release_id`。
- 移入 processed 的候选集合必须与批次清单一致。
- 必须通过规则去重、冲突、发布清单与交叉仓库兼容性检查。

任何无法分类的 PR 都失败关闭。

### 7.2 My-Video/main

完成一次性仓库统一后，`main` 必须启用：

- PR-only、必需测试、禁止强推与删除。
- Skill、工作台、工作流和发布配置由决策中枢账号 CODEOWNERS。
- 另一台电脑只允许读取发布版本；可以报告问题，但不能通过标准工作流发布。

Git Hook 作为本地快速反馈存在，但克隆后必须由安装命令设置 `core.hooksPath` 并校验 Hook 版本。Hook 缺失不能降低服务端检查标准。

## 8. 决策中枢的批次审阅事务

用户说“审阅候选规则”或“把候选迭代进正式规则”时：

1. 验证角色为 `decision-hub`，两个仓库已同步且待审工作树干净。
2. 从当前 CHEN-BRAIN SHA 生成不可变审阅批次 `governance/review-batches/RB-YYYYMMDD-短码.yaml`，列出本批候选 ID 与 blob SHA。
3. 审阅期间新合并的候选不进入本批，自动留给下一批。
4. 按主题聚类，检索相关 03、06、Skill、07 复盘和其他 open 候选。
5. 每条候选只能得到一个裁决；同义候选合并证据，冲突候选保留双方证据并作单一决定，禁止拼接折中规则。
6. 正式规则只保存精简的条件、动作、边界、例外、证据级别和状态；完整过程留在候选与单条视频日志。
7. 仅当启动流程、工具路由、成本、质量闸门或回流协议变化时修改 Skill；纯剪辑判断不得复制到 Skill。
8. 将本批候选移动到 processed，生成正式规则发布清单。
9. 在独立治理分支运行契约测试、重复与冲突检查、Skill 兼容检查和相关工作台测试。
10. 创建正式治理 PR；在合并前重新同步 main。新候选只造成 base 前进，不改变本批集合。
11. 所有检查通过后由决策中枢人工合并；失败时保留分支和批次，重新审阅，不强推。

当 open 候选达到 10 条或最老候选超过 14 天时，系统提醒决策中枢审阅，但不得自动晋升或删除候选。

## 9. 跨仓发布与一致性

Git 不能跨两个仓库原子提交，因此不使用“先后推送就算完成”的假设。CHEN-BRAIN 在 `governance/releases/<release_id>.yaml` 保存不可变发布记录，并由 `governance/current-release.yaml` 指向当前生效版本。发布记录结构为：

```yaml
schema_version: 1
release_id: MAX-RULES-YYYYMMDD-NNN
status: active
rules_schema: 1
skill_impact: none|required
minimum_my_video_commit: <40位提交SHA>
previous_release_id: <上一版本ID>
review_batch_id: <审阅批次ID>
```

发布协议：

### Skill 不受影响

1. CHEN-BRAIN 正式治理 PR 引用当前已发布的 My-Video 最低兼容 SHA。
2. 合并 CHEN-BRAIN PR 即激活新正式规则。

### Skill 或工作台受影响

1. 先在 My-Video 准备并测试兼容变更；新版本必须同时兼容上一规则发布和下一规则发布。
2. 先合并 My-Video PR，获得不可变提交 SHA。此时新能力处于兼容待用状态，不改变旧规则判断。
3. CHEN-BRAIN 正式治理 PR 的发布清单引用该 My-Video SHA。
4. 只有 CHEN-BRAIN PR 合并且 `status: active` 后，新规则才生效。

每条视频启动时验证：本机 My-Video HEAD 必须包含 `minimum_my_video_commit`，且发布清单结构有效。不满足时停止启动并给出同步指令，不退回旧规则猜测执行。

若无法实现上一版与下一版的兼容窗口，该变化必须拆成“先加入兼容能力、再激活规则、最后清理旧能力”三个独立发布，不允许一次性破坏式切换。

## 10. My-Video 仓库一次性统一

统一执行前必须重新测量本机 `main`、`codex/two-computer-sync` 与 `origin/main` 的 SHA、共同祖先、脏文件和未跟踪文件；规格中的历史观测值不能作为执行时常量。

统一流程：

1. 为三个提交点和本机独有改动创建可恢复备份引用与定向补丁。
2. 明确列出本机独有源码、文档和校准；不使用 `git add -A`，不暂存 `制作记录/`、Graphify 生成物或 `.superpowers/` 运行文件。
3. 旧源帧率审片实现、旧 Skill 和共享分支重复副本只进入恢复备份，不进入最终发布版本。
4. 从功能最完整的共享分支创建干净集成分支，定向合入本机独有修改。
5. 使用 `--allow-unrelated-histories` 合并原远端历史，逐文件解决初始化冲突并记录裁决，不重写任一历史。
6. 运行完整工作台测试、lint、构建、规则契约测试和 1080P/30fps 导出测试。
7. 通过普通 PR/普通推送把验证结果纳入 `origin/main`；若仍需强推，停止并视为统一设计或基线判断失败。
8. 两台电脑重新 clone 或快进到统一后的 `main`，验证 Skill、工作台和规则兼容清单。
9. 先保留所有备份引用与旧分支；两台电脑稳定运行后再由用户单独决定是否清理。
10. 最后启用 My-Video 的 main 分支保护，今后只从 `main` 读取发布版本。

## 11. NAS 镜像协议

只有用户明确说“把现有所有配置和规则同步到 NAS”时才执行镜像：

1. 读取 CHEN-BRAIN 当前 active 发布清单。
2. 验证 CHEN-BRAIN 与 My-Video 所需提交均存在且工作树中的生成文件不会进入镜像清单。
3. 只从已确认 Git 提交生成镜像，不从本机脏工作区复制规则正文。
4. 镜像清单记录 `release_id`、CHEN-BRAIN SHA、My-Video SHA、时间和文件摘要。
5. NAS 内容漂移时标记 REVIEW；禁止把 NAS 改动反向覆盖 Git。

## 12. 对抗性失败场景

### 双机同时提交候选

两个候选使用不同分支和唯一文件名。各自 PR 独立校验、顺序合并；后合并者由 GitHub 更新 base。若同名、ID 重复或差异越权，PR 失败，不覆盖。

### 另一台电脑误改正式规则

候选命令不会复制该改动；候选 PR 的服务端 diff 检查拒绝候选目录外的任何变化。正式路径受 CODEOWNERS 保护，不能随候选自动合并。

### 候选基于旧规则

候选记录启动 SHA 与提交 base SHA。决策中枢比较相关正式规则的差异；相关规则已经变化时，候选进入 REVIEW 或重新验证，不直接晋升。

### 候选互相冲突或重复

启动时最多读取 3 条且不混合冲突候选；提交时填写 `duplicate_of` 与 `conflicts_with`；审阅时按批次聚类并形成一个明确裁决。

### 审阅时又有新候选进入 main

审阅批次由 Candidate ID 与 blob SHA 冻结。新候选不进入当前批次，也不会因 rebase 被误移动到 processed。

### CHEN-BRAIN 已更新而 My-Video 未完成

规则发布清单只能引用已存在的 My-Video 提交。启动预检验证祖先关系；不兼容时停止。涉及 Skill 的发布先合入向后兼容能力，再激活 CHEN-BRAIN 规则。

### 推送竞争、断网或 PR 检查失败

本地提交和候选草稿保持可恢复；不强推、不自动改写正式文件。同步最新 main 后重新创建干净分支并重新校验。

### Hook 未安装或角色配置错误

启动预检会报警，但服务端仍按实际 diff 执行相同检查。服务端不相信本机角色字段。

### 误提交素材、密钥或机器路径

专用命令只接收一个 Markdown 候选；服务端同时检查路径、操作类型、扩展名、体积、秘密模式与绝对路径。发现风险时 PR 失败。

### 候选长期积压造成幻觉或 Token 膨胀

每次任务最多读取 3 条相关候选；processed 默认不参与启动读取；积压达到数量或时间阈值只提醒审阅，不自动摘要进正式层。

## 13. 验收标准

### 13.1 权限与路径

1. 两个仓库的 `main` 都拒绝直接 push、force push 和删除。
2. 决策中枢和 editor 使用不同 GitHub 身份；editor 账号不具备规则 bypass 能力。
3. editor 新增一个合规候选 PR 可以通过并自动合并。
4. editor 修改正式规则、processed、已有候选、工作流或多个文件时，服务端检查失败。
5. 本机 Hook 未安装时，服务端仍能拒绝同样的越权差异。

### 13.2 并发与恢复

6. 两个临时 clone 同时提交不同候选，两条候选都保留且没有手工内容合并。
7. 同名 Candidate ID、删除候选、修改候选、过期 base 和网络中断都失败关闭并保留可恢复状态。
8. 审阅批次生成后新进入的候选不会被当前批次移动或裁决。

### 13.3 规则质量与记忆

9. 新视频任务记录 CHEN-BRAIN SHA、My-Video SHA 和最多 3 个候选 ID。
10. 每条视频存在带 Token Budget 的 Goal，交付日志包含 Token、耗时、等待、转写、渲染、返工、成片时长与每分钟成片 Token 成本。
11. 正式规则优先级、候选冲突、重新基线化和用户单次例外都有明确日志。
12. 重复候选合并证据而不新增同义正式规则；冲突候选不被拼接。
13. processed 候选可追溯到审阅批次、发布 ID 和目标规则。

### 13.4 跨仓发布

14. `skill_impact: required` 时，CHEN-BRAIN 不得引用不存在或不兼容的 My-Video 提交。
15. My-Video 先发布而 CHEN-BRAIN 激活失败时，旧规则仍可正常运行。
16. 本机 My-Video 不包含最低兼容提交时，新视频启动被阻止。

### 13.5 仓库统一与媒体边界

17. My-Video `main` 保留本机、共享分支和原远端历史以及已确认的本机独有修改，无强推。
18. 完整测试、lint、构建与审片导出契约通过，审片输出仍固定为 1080P、30fps。
19. NAS、原片、EDL、成片、转写全文、缓存和历史产物未被移动、删除或提交。

## 14. 实施范围与顺序

后续实施必须拆成以下可独立验证的阶段：

1. 统一 My-Video 历史与 `main`，保留可恢复备份。
2. 在 CHEN-BRAIN 实现候选 schema、专用提交命令和治理检查。
3. 配置两个仓库的分支保护、CODEOWNERS 与必需状态检查。
4. 实现任务冻结读取、候选最多三条与任务日志契约。
5. 实现审阅批次、processed 冻结和规则发布清单。
6. 实现跨仓兼容检查与 NAS active-release 镜像。
7. 使用两个临时 clone 完成并发、越权、断网和跨仓失败演练。
8. 两台真实电脑分别执行最小接入验证，再开始长期剪辑。

在以上验收全部通过前，不宣称双机协同机制已经彻底生效；现有文档约定继续作为临时操作边界。
