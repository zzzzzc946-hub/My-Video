# 双机剪辑规则协同与仓库统一设计

## 目标

两台电脑都能长期剪辑并持续沉淀经验，但任何候选都不能静默覆盖正式规则；当前电脑继续作为唯一决策中枢，负责正式规则、Skill 和工作台版本发布。

本设计不承诺网络或 Git 永远不发生并发竞争。它保证的是：竞争会被检测并停止，不会静默覆盖；未经裁决的内容不会进入正式规则层。

## 不可破坏的系统约束

1. `CHEN-BRAIN/main` 是 MAX 正式知识与规则的唯一真源。
2. `My-Video/main` 是工作台代码和 `max-jianji-skill` 发布版本的唯一真源。
3. 当前电脑是决策中枢；只有它能修改正式 `00–07`、处理候选、发布 Skill 与工作台。
4. 另一台电脑是长期剪辑节点；可以持续读取全部正式规则和相关候选，但只能新增候选文件。
5. NAS 只接收 Git 已确认提交的阶段性镜像，不参与规则写入或冲突裁决。
6. 原片、原始 EDL、成片、转写和渲染缓存不进入规则仓库，也不因仓库统一而移动或改写。
7. 所有审片版本继续固定为 1080P、30 fps。

## 双层规则模型

### 正式层

正式层包括：

- `00｜MAX剪辑系统入口与读取顺序.md`
- `01｜MAX剪辑画像.md`
- `02｜MAX账号与受众.md`
- `03｜MAX粗剪判断标准.md`
- `04｜MAX自有视频案例库.md`
- `05｜外部对标视频案例库.md`
- `06｜MAX剪辑反馈与校准库.md`
- `07｜视频复盘索引.md` 与已裁决归档
- `max-jianji-skill/SKILL.md`

正式层只能由决策中枢修改。Skill 只保存启动顺序、工具路由、成本、质量与回流流程；具体剪辑判断以 CHEN-BRAIN 正式层为准，避免同一规则在两个仓库重复维护。

### 候选层

候选层位于：

```text
08｜规则候选收件箱/open/
08｜规则候选收件箱/processed/
```

另一台电脑只允许在 `open/` 新增文件，不允许修改、覆盖或删除已有候选，也不更新公共索引。候选文件采用唯一名称：

```text
CR-YYYYMMDD-HHMMSS-机器ID-视频ID-随机短码.md
```

候选必填字段：

- Candidate ID
- 机器 ID
- 视频 ID 与日志路径
- 视频启动时读取的正式规则 SHA
- 提交时同步到的远端 SHA
- 主题标签、内容类型与剪辑难点
- 用户原始反馈与可验证证据
- 建议判断（条件 → 动作）
- 适用范围、例外与反例
- 关联正式规则、校准和历史复盘
- 已知冲突与不确定项
- 是否在本条视频中试用及结果
- 初始状态：`OPEN / REVIEW`

## 新视频读取顺序

两台电脑每条视频启动都执行：

1. 对 CHEN-BRAIN 执行 `git fetch` 和 `git pull --ff-only`，记录正式规则 SHA。
2. 对 My-Video 执行只读同步，记录 Skill/工作台 SHA；另一台电脑不得在该仓库提交。
3. 读取正式 `00`，按路由读取相关 `01/02/03/06` 与已裁决复盘。
4. 根据主题、内容类型、剪辑难点和反馈类型，定向读取少量相关 `08/open` 候选。
5. 在任务日志记录读取的正式 SHA、候选 ID、采用/未采用理由和冲突状态。

判断优先级固定为：

```text
当前用户明确指令
→ 正式硬边界与稳定规则
→ 已确认校准
→ OPEN 候选
```

候选可以触发额外检查、保守处理或有记录的实验，但不能覆盖正式规则。候选与正式规则冲突时，正式规则优先，本条标记 `REVIEW`。候选之间冲突时不得混合执行，只记录分歧并等待决策中枢裁决。

## 另一台电脑的候选提交事务

候选提交必须通过专用命令完成，禁止通用 `git add -A`：

1. 检查本机角色为 `editor`。
2. 确认工作区除候选新文件外没有待提交变化。
3. `fetch` 并快进同步正式 `main`；禁止自动合并正式文件。
4. 根据模板生成唯一候选文件。
5. 校验必填字段、文件名、路径和状态。
6. 只暂存该一个候选文件。
7. 检查暂存差异只有 `08/open/<Candidate ID>.md` 的新增，没有修改或删除。
8. 提交后再次 `pull --rebase`；只允许 Git 自动处理不同文件的追加。
9. 推送失败时停止并报告，不强推、不自动解决正式文件冲突。

本机角色由被 Git 忽略的 `config/machine-role.json` 指定：

```json
{ "role": "decision-hub", "machineId": "max-primary" }
```

另一台电脑使用：

```json
{ "role": "editor", "machineId": "max-secondary" }
```

## 决策中枢的周期审阅事务

用户说“审阅候选规则”或“把候选迭代进正式规则”时：

1. 确认角色为 `decision-hub`，两个仓库工作区干净且均已同步。
2. 为本次审阅记录正式规则 SHA 和候选集合快照。
3. 按主题聚类候选，检索相关 `03`、`06`、Skill 与历史复盘。
4. 对每条候选只给出一个裁决：不写入、合并证据、新建 F1、修订/升级、本条经验。
5. 同义候选合并证据；冲突候选保留双方证据与明确裁决，不拼接折中规则。
6. 更新正式规则和关联复盘；仅在执行流程或工具路由受影响时更新 Skill。
7. 将候选移动到 `processed/`，在原文件中追加裁决、目标规则 SHA 和生效版本。
8. 运行规则契约测试、Skill 测试和相关工作台测试。
9. 先提交 CHEN-BRAIN，再提交 My-Video；任一推送被拒绝都停止、重新拉取并复审，不强推。

## 自动防错机制

实现三层约束：

1. **命令层：** 候选提交命令只接收新候选路径，不提供正式规则写入参数。
2. **Git Hook 层：** `editor` 角色提交时，如果暂存区包含 `08/open/` 以外路径、修改、重命名或删除，提交失败。
3. **CI 层：** 候选提交契约测试验证路径、操作类型、模板字段和唯一 Candidate ID；正式规则变化必须同时包含裁决关联和决策中枢审阅记录。

同一 GitHub 账号无法从服务端可靠区分两台物理电脑，因此本设计不把账号身份当机器角色。机器角色来自本机配置，真正的安全边界由“专用命令 + 暂存区检查 + CI 契约 + 唯一文件追加”共同提供。

## My-Video 仓库一次性统一

当前状态包含三个层次：本机脏 `main`、领先 22 个提交的 `codex/two-computer-sync`、以及与本机无共同祖先的 `origin/main`。

统一流程：

1. 为三个提交点创建可恢复备份引用。
2. 只保全本机独有源码/文档；不暂存 4.3GB `制作记录/`、Graphify 生成物或 `.superpowers/` 运行文件。
3. 旧的源帧率实现、旧 Skill 和共享分支重复副本只进入定向恢复备份，不进入最终版本。
4. 从 `codex/two-computer-sync` 创建干净集成分支并合入本机独有修改。
5. 使用 `--allow-unrelated-histories` 合并 `origin/main`，保留两套历史。
6. 已模拟出的六个初始化冲突采用共享分支新版：`.gitignore`、`README.md`、两份旧计划、`package.json`、`package-lock.json`。
7. 运行完整工作台测试、lint 和构建。
8. 本机 `main` 仅用快进方式指向验证后的集成结果，并设置 `origin/main` upstream。
9. 先保留定向备份和旧分支；确认两台电脑均正常后再单独决定是否清理。
10. 推送远端 `main` 必须是普通推送；如果仍需强推，视为设计失败并停止。

## 对抗性失败场景

### 两台电脑同时提交候选

候选使用唯一文件名且只追加。后提交者 `pull --rebase`；如果 Git 不能自动处理，停止并报告，不覆盖。

### 另一台电脑误改正式规则

本机 Hook 在提交前拒绝；CI 再次拒绝路径越权。已存在于工作区的误改不会被候选提交命令暂存。

### 候选基于旧规则制作

候选同时记录“视频启动规则 SHA”和“提交时远端 SHA”。决策中枢审阅时比较差异；相关正式规则已变化则候选自动进入 REVIEW，不直接升级。

### 候选与正式规则冲突

执行时正式规则优先；审阅时保留冲突证据并作单一裁决。禁止静默覆盖、折中拼接或仅按文件更新时间决定。

### Skill 与 CHEN-BRAIN 不一致

具体剪辑判断以 CHEN-BRAIN 为准。Skill 只负责流程；测试禁止 Skill 复制未关联的正式判断。涉及流程变化时，CHEN-BRAIN 裁决提交必须明确标记 `Skill impact`。

### 推送竞争或网络中断

所有写入先形成本地提交。推送失败不重写历史；重新同步后复审差异。任何脚本都不调用 `push --force`。

### 误提交素材、密钥或机器路径

候选提交命令只暂存一个 Markdown 文件；CI 拒绝视频、音频、密钥、`.env`、NAS 私有配置和候选目录外文件。

## 验收标准

1. My-Video `main` 同时包含本机历史、GitHub 历史、共享分支功能和本机独有校准，且无强推。
2. 工作台完整测试、lint、构建通过；审片默认仍为1080P/30fps。
3. `editor` 角色新增合规候选成功，修改正式规则失败，提交多个文件失败，删除候选失败。
4. `decision-hub` 能批量审阅候选、去重、裁决、移动到 processed，并更新正式规则。
5. 新视频任务能同时记录正式规则 SHA 与相关候选 ID；候选冲突时产生 REVIEW。
6. 两台电脑都只从 My-Video `main` 读取发布 Skill；另一台电脑无法通过标准工作流发布 Skill。
7. NAS、素材、EDL、成片和历史产物未被移动、删除或提交。
8. 所有失败路径都停止并保留可恢复状态，不自动强推、不静默覆盖。
